# CS-03 Worker–Neon Function 共有秘密の登録・更新・停止手順（2026-11-23）

**状態：手順案確定／実クラウド操作未実施／NO-GO。** この資料はデプロイ、クラウド設定更新、秘密値の生成・登録・共有の承認ではない。必要なサービス権限・環境変数UI/APIの具体的な画面は実際の対象サービスで個別に確認する。

## 1. 対象と境界

| 対象 | 環境変数／設定名 | 扱い |
|---|---|---|
| 専用Cloudflare Certification-StudyアカウントのCS-03 Worker | `CS03_GATEWAY_SECRET` | **Secret**。Worker側だけで保持し、上流送信時に `x-secret` として付与 |
| 隔離Neon Function（隔離branch `br-snowy-truth-a162pmdt`） | `CS03_ORIGIN_SECRET` | **Secret**。HTTP `x-secret` と定数時間で照合。実行時に `process.env` から取得する現行実装 |
| CS-03ブラウザ（GitHub Pages） | なし | **秘密を配布しない**。ブラウザはJWTのみ。公開 `cs03-config.js` は `previewEnabled:false` のまま |
| 開発PCとGitHub | なし | 実秘密をソース・テスト・設定サンプル・コミット・Actions・履歴・標準出力・ログに残さない |

本秘密は**Worker→Functionの経路識別用**であり、ユーザー本人を確認するJWT、Neon DBのRLS、WorkerのDOレート上限を代替しない。Origin検査だけも認証にはならない。

現行実装の制約：`functions/cs03-progress.mjs` は最低32 **UTF-8 bytes**、**完全一致する単一値のみ**受理する。Worker側の`server/cs03-trusted-edge-gateway.mjs`も32 UTF-8 bytes以上を要求。バージョン付き複数秘密の同時受入れには**現時点で対応していない**。

## 2. 初回登録（**将来、隔離配置が別途承認された場合のみ**）

1. **配備前の読み取り照合**：Cloudflareのアカウントが専用Certification-Studyであること、Workers・DOがFreeであることを対象画面で再確認。Neonは専用Certification-Studyプロジェクト／非default branch／`cs03_auth_sandbox`／`cs03_progress_api`のみ。専用Account ID照合ガードも実行するが、これだけで別アカウント操作を防げない。
2. **非公開・停止状態**：`workers_dev:false`、`preview_urls:false`、未承認routeなし、GitHub PagesのCS-03プレビューOFFを維持。仮に実Function URLが存在しても秘密検証が機能するまでブラウザからの接続を有効化しない。
3. **新しいランダム値**：承認済みの信頼できる端末・安全な生成手段で、推測不能な暗号学的乱数を**32 bytes以上**生成。サービス間で同一の値を用いる（個々に別々に生成しない）。値をチャット・スクリーンショット・GitHub・Issue・console・ログへ表示しない。秘密ファイルを作る場合はアクセス制限と即時安全削除の計画が必要。
4. **登録先を個別に確認**：Cloudflare専用Workerのserver-side secret `CS03_GATEWAY_SECRET` と、隔離Neon Function実行環境のsecret `CS03_ORIGIN_SECRET` に同じ値を安全な管理画面／シークレット登録手段で保存。Neon Functions側で`process.env`経由で参照できること、secretが平文公開されないことは**配置前に正式な仕様と対象画面で確認**。DB接続文字列 `CS03_TEST_DATABASE_URL` は別の秘密として専用隔離DBに限定。
5. **検証順**：値自体を表示せずに**存在・スコープ・参照権限**を確認。実際の値一致は将来の承認済み隔離テストで、秘密なし／誤秘密が401、正秘密＋有効JWT＋正Originのみ期待通り動くことから確認する。エラーレスポンスやログに秘密を含まない。
6. **公開前の追加受入れ**：DOの原子的制限、実Cloudflare ingress、実routeのfail-closed、無料枠超過時のふるまい、Neon Functions URL所有先、DBのRLS、通信経路/CSP、復旧停止を独立確認。**秘密が一致しても公開GOではない。**

## 3. 定期・緊急の秘密更新（単一値しか受理しない現行実装）

**重要：現行コードでWorker側だけ先に更新すると、Neon Functionは旧値を期待するため通信が失敗する。Function側だけ先に更新しても同様。サービス間で一時的に通信が止まることを受け入れる「停止型更新」とする。** 無停止で更新したい場合は「新旧両方を受け入れる期間」を持つ別設計と独立試験が必要であり、現時点では採用しない。

1. 事前に運営者の**対象と手順を明示した個別承認**を受ける。事故時はCS-03だけの影響範囲と漏えい疑いを確定し、秘密はチャットで受け取らない。
2. まずCS-03公開導線をOFFにし、**Neon Functionを含む旧秘密での新規処理が止まることを確認**する。Workerを止めるだけではFunctionへの直接到達を防げない。遮断確認前に更新作業を開始しない。
3. 別の新ランダム値（32 bytes以上）を安全に生成して、**両方のサービス側の秘密を差し替える**。旧値をログや画面に表示しない。失効/削除できない場合は遮断継続。
4. 隔離テストのみで、旧値不許可、新値と有効JWTの組合わせだけ許可、不一致時401、DO/DBに不正アクセスなしを確認。**旧値は受理させない**。
5. 監査記録には更新時刻、影響した秘密名、実施権限、確認結果、承認番号、復旧判断のみ記録する。値・ハッシュ・JWT・DB URLは記録しない。
6. 再開は別途承認後。ブラウザの自動再送や滞留下書きの自動上書きはしない。接続断時は確認待ちデータを保持する。

## 4. 緊急停止・復旧できない場合

- 不正なアクセス・漏えい疑い・課金異常・DB経路不整合・DO停止では**Fail Closed**。公開導線OFFだけでなく、Functionへの直接呼び出しが拒否されていることを確認する。
- 一方の秘密だけ更新済み／Neonの秘密管理方式が未確認／失効を確認できない場合、**復旧せずCS-03同期を停止したまま**にする。既存の端末内学習は維持し、未保存データは手動で保全する。
- 事故後の旧秘密の漏えい疑いがある場合、旧値を元に戻さない。新しい値での安全な再構築と再受入れが必要。
- 本番のCloudflare・Neonでの秘密取り扱い、実際の保存先・設定UI/API・ロールバック可否・値反映の遅延は未確認。仕様が確定するまでは手順に実際の書込みコマンドを載せない。
